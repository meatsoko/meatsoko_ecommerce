## Section A — Known bugs & unverified fixes

Highest priority: these affect correctness of things users actually do.

1. **Sign-Out bottom sheet — fix applied, not cleanly confirmed.** `LogoutCustomBottomSheetWidget` was switched from `showModalBottomSheet` (which was silently swallowing taps on its own buttons) to `showGeneralDialog`. Observed working across repeated test rounds, but the final manual confirmation pass was noisy — treat as fix-applied-and-probably-working, not verified clean. **Also unaddressed:** the other ~17 `showModalBottomSheet` call sites in `more_screen_view_new.dart` were never checked for the same underlying issue. (`CLAUDE.md` §4/§6 item 1; `mobile_customization_log.md`)

2. **Two confirmed crash-risk switch statements.** Both throw `UnimplementedError()` for a specific enum value that the type system allows and the API can plausibly return:
   - `vendor_app/lib/features/auction/screens/auction_sales_report_screen.dart:409` — `AuctionStatus.all`
   - `vendor_app/lib/features/auction/widgets/auction_status_widget.dart:69` — `AuctionStatus.recreated`
   If either status reaches these code paths, the screen crashes outright. Verified directly by reading both files.

3. **Blank error messages on certificate/connection failures.** `ApiErrorHandler.getMessage` leaves `errorDescription` empty for two `DioExceptionType` cases, so a real SSL/cert failure or no-connectivity error shows the user nothing:
   - `user_app/lib/data/datasource/remote/exception/api_error_handler.dart:97-100` — `badCertificate` and `connectionError`, both `// TODO: Handle this case.`
   - `vendor_app/lib/data/datasource/remote/exception/api_error_handler.dart:97-104` — same two, **plus `unknown`** also left blank (worse than user_app, which at least sets a message for `unknown`).
   Verified directly by reading both files.

4. **Vendor app login/registration — asserted parity, not independently re-verified live.** The User app's registration/login was reproduced end-to-end with `adb logcat` evidence (2026-08-31). The Vendor app's equivalent rename/rebrand work is asserted "high confidence, behaves identically" but was not re-run live on an emulator the same way.

5. **Vendor app iOS Universal Links** are tied to `applinks:6valley-install.6amdev.xyz`, a domain owned by the template vendor (6amTech), not MeatSoko — these deep links cannot resolve for MeatSoko regardless of any other fix.

The real, working screen is `user_app/lib/features/home/screens/view_all_product_screen.dart` (99 lines), which is what `route_healper.dart:50` actually routes to. 3. **Disabled surface area from the recent product-details redesign** (commit `cb0c935a`, "redesign product details page, fix add-to-cart & loading-flash bugs"). In `user_app/lib/features/product_details/screens/product_details_screen.dart:4-29`, ~10 imports are commented out with explanatory notes, and the related-products fetch call (line ~72-75) is disabled. Concretely, customers can no longer reach from the product details page: the Specifications section, Related Products row, on-page Reviews-and-Specification widget, the YouTube video widget, the "more from this shop" list, and the Promise widget. This looks intentional (design decision, not an accidental break) but represents real functional surface area that quietly disappeared — worth an explicit decision on whether it comes back in the new design or is cut for good.

4. **Uncommitted, local:** an "Address" quick-action card on the More screen is commented out in `user_app/lib/features/more/screens/more_screen_view_new.dart:224-238` with a note to re-enable later. (Confirmed still present/uncommitted as of this audit via `git status`.)

5. **Pending cleanup TODOs left in shipped code:**
   - `vendor_app/lib/features/order_details/widgets/payment_status_widget.dart:372` — `// ToDo: Offline payment info display logic is currently disabled. Enable it`
   - Both apps' `order_payment_info_widget.dart` (`vendor_app` line 110 / `user_app` line 112) — `/// Todo: remove payment status and method from here as per new design`, not yet done in either app.
   - `vendor_app/lib/features/shop/widgets/shop_information_widget.dart:16` — `// todo: Delete this widget`, still present.

6. **Hardcoded/provisional values:**
   - `user_app/lib/features/auction_search/domain/models/auction_filter_param_model.dart:42-43` — auction price and entry-fee caps hardcoded to `1000` with a note this should come from server config instead.
   - `vendor_app/lib/features/auction/widgets/billing_info_widget.dart:17` — hardcoded tax value; comment says use `_calculateTax()` once the API provides real tax details.
   - `vendor_app/lib/utill/app_constants.dart:181` — `/// TODO: update the below URI when the API is ready`, sitting above 8 auction-fulfillment endpoint constants (tracking upload, address update, payment status, delivery status, invoice generation, cancel, sales report, transaction history). Verified directly — these endpoints may be provisional/unconfirmed against the real backend.
   - `vendor_app/lib/features/auction/screens/addAuctionProduct/auction_info_screen.dart:40` — a hardcoded `['English', 'Arabic']` list feeds a `TabController`, rather than deriving from the app's actually-configured languages.
   - `user_app/lib/features/product_details/widgets/product_title_widget.dart:539-542` — "Customize" and "More Details" labels are hardcoded English, deliberately bypassing `getTranslated` (comment explains: no existing key fits, and adding one means touching every bundled language file for one label). Verified directly. Not reflected in any of the 5 locale files.

7. **Template-wide boilerplate (low individual risk, noted once):** roughly 35 repository files across both apps implement a generic `RepositoryInterface` with `add()/delete()/get()/getList()/update()` methods that just `throw UnimplementedError()`. Confirmed this is a 6valley-template-wide pattern — the repositories actually used in the app override these with real, differently-signatured methods elsewhere in the same class, and the generic stub signatures are never called today. Not an active bug, but a landmine: any future code that calls the generic interface method on these repos will crash immediately with no guardrail.

8. **No Swahili localization** despite this being a Kenyan storefront — flagged explicitly in both `blueprint_user_app.md` and `blueprint_vendor_app.md`. All 5 shipped locales (ar, bn, en, es, hi) have matching key counts (no missing-key gaps within what exists), Swahili is simply absent as an option.

9. **M-Pesa mobile integration status — needs re-check, not asserted.** `mobile_apps.md` (stale) claims there is no native M-Pesa mobile integration, only a generic offline-payment/webview workaround. Given that doc's other claims are known-superseded, this specific one should be independently re-verified rather than trusted as still true.

## Section C — Branding / config gaps

1. **App icons and splash screen** still show default/6valley artwork, not MeatSoko branding. (`CLAUDE.md` §4 "Not started")

2. **Facebook App ID** is still the literal placeholder `YOUR_APP_ID` in both `strings.xml` and `Info.plist`. As a direct consequence, Facebook login is forced off in code: `user_app/lib/features/auth/widgets/only_social_login_widget.dart:66-70` and `social_login_widget.dart:71,110,150` all hardcode the toggle to `0`/off. Needs either real credentials or the feature formally removed.

3. **Two independent version strings per app, no auto-sync** — `pubspec.yaml`'s `version:` (store metadata) and `AppConstants.appVersion` (drives the in-app forced-update check). This is a standing operational risk, not a one-time fixed bug: the server-side minimum-version gate (Admin → System Setup → App Settings) must stay ≤ the app's actual version or every user gets walled into an unusable forced-update screen — this has already happened once in production and was fixed manually. (`CLAUDE.md` §7)

4. **`vendor_app/pubspec.yaml` has version-resolution smells** suggesting a past dependency conflict was patched over rather than resolved:
   - `textfield_tags: 2.0.2` — hard-pinned with no caret, unlike every other dependency.
   - `collection: any` — unconstrained, unusual and sloppy.
   - `dependency_overrides: syncfusion_flutter_core: ^33.2.8` forced, even though all Syncfusion packages are already pinned to `^33.2.8` — the override wouldn't be needed if resolution worked cleanly on its own.

## Section D — Platform / build gaps

1. **iOS does not build on either app.** Root cause: a Swift Package Manager / Firebase version conflict — `firebase_messaging` wants `firebase-ios-sdk` 12.17.0, but resolution picks an incompatible 12.15.0+. `disable-swift-package-manager: true` is already set in `pubspec.yaml` and does **not** fix it. Root cause not fully diagnosed. Android is the only reliably testable platform right now — a clean `flutter analyze` is not proof the app builds on iOS. (`CLAUDE.md` §4/§7)

2. **Zero real test coverage in either app.** Both apps only carry the unmodified default `flutter create` counter-app smoke test. Noted here as a platform/process gap because it affects confidence in every other item in this document — every bug above was found by manual testing or code reading, not caught by CI.
