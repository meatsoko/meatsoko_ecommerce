Executive Summary

The app is functionally complete and structurally sound for a first release. Static analysis reports zero compile errors (28 warnings, 37 informational — all lint-level). The production backend is healthy, not in maintenance mode, and correctly configured for Kenya: KES currency, multi-vendor mode, guest checkout enabled. App Links are live and independently verified by Google's own Digital Asset Links API. Release signing, Maps, and policy pages are all complete.

The largest risk is not code quality but unverified runtime behaviour. Payments are the clearest example: M-Pesa and Paystack have no native implementation in the app at all — checkout hands off to a server-hosted payment page inside a WebView. That is a legitimate design, but it means the single most business-critical flow cannot be validated by code inspection and must be tested end-to-end on a device against a real transaction before launch.

There is also no crash reporting in the build. Combined with no automated test coverage, the first production issue will surface as a customer complaint rather than a dashboard alert.

Payments — Most Important Finding

M-Pesa and Paystack have no native implementation in the app. Searching the entire codebase for mpesa returns zero matches. paystack appears exactly once — as an image asset path.

Payment is generic: checkout opens a screen that loads a server-hosted payment page in a WebView and detects completion by inspecting the URL for success / fail / cancel plus a token.

Three consequences for release:

  • Gateway behaviour is entirely backend-owned — correctness cannot be inferred from app source.
  • Completion detection is string-matching on URLs, which is brittle if backend callback URLs change.
  • The payment WebView runs under a globally permissive cleartext-HTTP policy (see issue P1 #3).

Deep Links — Verified

The manifest declares shop.meatsokogroup.com in an auto-verifying filter covering product, vendor-shop, order-tracking, referral-login, and auction paths. The live assetlinks.json serves valid JSON with the correct package name and production certificate fingerprint, and Google's Digital Asset Links API resolves the statement with no errors.

Play App Signing caveat Only the upload certificate is currently listed. If you enrol in Play App Signing, Google re-signs the app and devices check its fingerprint instead — deep links would keep working for sideloaded builds but silently fail for everyone installing from the Play Store. Add that fingerprint on enrolment.

Manual QA Checklist

21 concrete test cases. The six payment cases are non-negotiable before release.

Payments — critical, nothing here is statically verifiable

  1. Complete a real M-Pesa STK Push order end-to-end; confirm the WebView returns and the order is created.
  2. Cancel an M-Pesa payment mid-flow; confirm the app recovers and does not create a phantom order.
  3. Complete a Paystack order end-to-end.
  4. Place a cash-on-delivery order.
  5. Pay using wallet balance.
  6. Force a payment failure; confirm success/fail/cancel detection fires correctly.

Authentication

  1. Register a new account; confirm the session persists across an app restart.
  2. Google Sign-In on a real device.
  3. Logout via the account screen — confirm both "Sign Out" and "Cancel" respond (known-flaky).
  4. Password reset via OTP.
  5. Guest browse → add to cart → guest checkout.
  6. Account deletion (Play Store compliance requirement).

Shopping & orders

  1. Browse categories and confirm real catalog data loads (not verifiable anonymously).
  2. Search, open a product, add to cart with variations.
  3. Apply a coupon; confirm totals recalculate.
  4. Place order → view history → open details → track.
  5. Cancel an order; request a refund from order details.

Maps, notifications, deep links

  1. Grant location permission; confirm the map renders with the new API key.
  2. Pick a delivery address on the map; confirm geocoding resolves.
  3. Receive a push notification in foreground and background; confirm tap-through.
  4. Open a product link from an external app — must open the app, not a browser.

Known Issues by Priority

P0 — Release blocker
  1. Launcher icon is 6valley template artwork. No adaptive icon variant. The app's pubspec.yaml has no icon-generator configuration and no source icon asset exists — this needs artwork and configuration before a generator can run.
P1 — Should fix before launch
  1. No crash reporting. Firebase Core is already wired, so adding Crashlytics is a small change with high operational value.
  2. Cleartext HTTP permitted globally — especially relevant since payments run inside a WebView.
  3. Facebook placeholders remain in Android string resources, masked by a hardcoded client-side override. Get real credentials or remove the feature.
  4. Blank error messages on certificate and connection failures — users see nothing when the network fails.
  5. Logout unconfirmed, plus roughly 17 unaudited modal call sites sharing the suspected root cause.
  6. No release minification or shrinking — larger artifact, no obfuscation.
P2 — Post-launch
  1. Empty Play update link — set immediately after first publish, or the next version bump strands users on a dead prompt.
  2. Only the upload certificate in assetlinks.json — add Play App Signing's fingerprint on enrolment.
  3. Permissions hygiene: no version caps on storage permissions; legacy Bluetooth permissions against a modern target SDK.
  4. Zero automated test coverage beyond the default scaffold smoke test.
  5. 28 unguarded debug print statements.
P3 — Polish
  1. Five zero-byte Dart files.
  2. No Swahili localization for a Kenya-first product.
  3. 14 substantive TODO/FIXME comments (excluding 157 template CRUD stubs).
  4. Hardcoded auction filter caps.
